# Onboarding: nuovo store e nuovi account

Guida operativa per chi deve **creare un nuovo store cliente** o **aggiungere un nuovo account** (manager/chef) a uno store esistente. Copre lo stato attuale del progetto: la creazione di un nuovo store è un endpoint API, l'aggiunta e la gestione degli account di uno store esistente sono a carico del manager (pagina Staff / `/v1/staff`, vedi sezione 2); la procedura manuale su Keycloak resta come alternativa per l'admin.

## 1. Creare un nuovo store (+ primo account manager)

Endpoint: `POST /onboarding/stores`
Permesso richiesto: `ADMIN_ALL` (ruolo `admin`), riservato al team interno.
Implementazione: {mod}`app.modules.onboarding.service`, {mod}`app.modules.onboarding.router`.

Crea in un'unica chiamata:
- la riga `Store` in Postgres (con uno `slug` univoco derivato dal nome, con retry automatico in caso di collisione);
- il primo account Keycloak con ruolo `manager`, con username finale `{slug-store}.{username}` (issue #81 — lo username Keycloak è univoco per realm, quindi va sempre prefissato con lo slug dello store).

```bash
TOKEN="<bearer-token-admin>"

curl -X POST http://localhost:8000/onboarding/stores \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{
    "store_name": "Trattoria da Mario",
    "manager": {
      "username": "mario",
      "email": "mario@example.com"
    }
  }'
```

Risposta (`OnboardingResponse`):

```json
{
  "store_id": 12,
  "store_slug": "trattoria-da-mario",
  "manager_username": "trattoria-da-mario.mario",
  "temporary_password": "xxxxxxxxxxxxxxxx"
}
```

Note importanti:
- `temporary_password` viene restituita **una sola volta** in questa risposta e non va mai loggata: consegnala al cliente su un canale sicuro. L'account ha `temporary=true`, quindi Keycloak forza il cambio password al primo login.
- Se la creazione dell'utente Keycloak fallisce dopo che lo `Store` è già stato committato, il servizio esegue un rollback compensativo cancellando lo `Store` appena creato (i due sistemi non condividono una transazione).
- Se `username` o `email` sono già in uso, l'endpoint risponde `409`.

## 2. Account dello staff (gestione da parte del manager)

Endpoint: `/v1/staff` (permesso `STAFF_MANAGE`, concesso al ruolo `manager`). Nella web UI è la pagina **Staff** (`#/staff`). Implementazione: {mod}`app.modules.staff.service`, {mod}`app.modules.staff.router`.

Il manager vede e gestisce gli account `chef`/`manager` del **proprio** store:

| Azione | Endpoint |
|---|---|
| Elenco (attivi e disattivati) | `GET /v1/staff` |
| Creazione | `POST /v1/staff` |
| Cambio ruolo chef/manager | `PATCH /v1/staff/{id}` |
| Disattiva / riattiva | `POST /v1/staff/{id}/deactivate` · `/activate` |
| Reset password | `POST /v1/staff/{id}/reset-password` |
| Eliminazione | `DELETE /v1/staff/{id}` |

Flusso di creazione: il manager inserisce nome, cognome, username (solo `a-z 0-9 _ -`), ruolo ed email opzionale. Lo username finale è `{slug-store}.{username}` (issue #81). La risposta contiene `temporary_password` **una sola volta**: non c'è SMTP, quindi il manager la **comunica a voce** (o su un canale sicuro) alla persona, che deve cambiarla al primo login (`UPDATE_PASSWORD`). Stessa regola per il reset password. La password non viene mai loggata.

Regole:
- Ruoli assegnabili: solo `chef` e `manager`, mai `admin`.
- Nessuna azione sul proprio account (disattivazione, eliminazione, cambio ruolo, reset password).
- Non si può disattivare né declassare l'ultimo manager attivo dello store.
- Massimo 20 account attivi per store (quelli disattivati non contano; vale anche per la riattivazione).
- `DELETE` solo su account già disattivato.
- Utenti di altri store o con ruolo `admin` rispondono `404`.
- Username o email già in uso: `409`.

Come funziona: Keycloak è la fonte di verità (utenti trovati tramite l'attributo `store_id`, nessuna tabella locale) e viene riusato il service account dell'onboarding, quindi **nessuna nuova variabile d'ambiente** (`terraform/ssm.tf`, `.env.example` e `render_env_from_ssm.sh` invariati). Le scritture sono serializzate per store con un lock advisory Postgres. Gli errori Keycloak seguono lo standard dei servizi esterni: 502, errore nel log del server e, in produzione, `details` ed eccezione originale mascherati da `AppError` (issue #373). Audit: riga di log strutturata `Staff audit: ...` (chi, cosa, su chi), nessuna tabella.

**Finestra residua dopo la disattivazione.** Disattivazione, eliminazione, cambio ruolo e reset password revocano le sessioni Keycloak dell'utente (il refresh non è più possibile), ma l'access token già emesso resta valido fino alla sua scadenza naturale, di norma pochi minuti: per quel tempo l'utente può ancora chiamare l'API.

**502 dopo la scrittura.** Se disattivazione, cambio ruolo o reset password rispondono 502 la modifica può essere già applicata ma le sessioni non revocate: riprovare l'operazione (la revoca viene rieseguita, anche con lo stesso ruolo).

**Email duplicata.** L'unicità dell'email è verificata su tutto il realm: un 409 può quindi rivelare che un indirizzo è già usato da un altro store (compromesso accettato).

### Alternativa manuale (admin, Keycloak Admin Console)

Se serve intervenire senza passare dal manager:

1. Vai su `${KEYCLOAK_URL}/admin/{realm}/console` (login con `KEYCLOAK_ADMIN` / `KEYCLOAK_ADMIN_PASSWORD`).
2. **Users → Add user**:
   - `Username`: `{slug-store}.{nome}` (es. `trattoria-da-mario.luigi`) — rispetta sempre questa convenzione, altrimenti l'utente rischia collisioni con account di altri store.
   - `First name` / `Last name`: obbligatori — sono le claim `given_name`/`family_name` da cui il backend deriva `operator_name`, mostrato nei log HACCP (batch, preparazioni).
   - `Email`: opzionale (non usata come credenziale, solo profilo).
   - Attribute `store_id`: **lista** con l'id numerico dello store (es. `["12"]`). È il claim che il backend legge per il multi-tenancy.
3. **Credentials tab**: imposta una password, marcala `Temporary` così l'utente la cambia al primo accesso.
4. **Role mapping tab**: assegna esattamente uno tra i realm role `chef` / `manager` / `admin`. Se manca un ruolo riconosciuto, il backend tratta l'utente come `"user"` senza permessi (vedi `_determine_role` in {mod}`app.modules.auth.dependencies`).

Verifica rapida via API (equivalente a quanto sopra, utile per script di provisioning): vedi `scripts/init_keycloak.py` per un esempio completo di creazione utente + assegnazione ruolo via Keycloak Admin REST API.

## 3. Riferimento rapido: variabili d'ambiente coinvolte

| Variabile | Uso |
|---|---|
| `KEYCLOAK_URL` / `KEYCLOAK_INTERNAL_URL` | Base URL Admin Console e API |
| `KEYCLOAK_REALM` | Realm applicativo (condiviso da tutti gli store) |
| `KEYCLOAK_ADMIN` / `KEYCLOAK_ADMIN_PASSWORD` | Credenziali admin master, solo per operazioni manuali/script (mai usate dall'app in runtime) |
| `KEYCLOAK_ONBOARDING_CLIENT_ID` / `KEYCLOAK_ONBOARDING_CLIENT_SECRET` | Service account scoped (`manage-users` + `view-realm`) usato da `POST /onboarding/stores` e da `/v1/staff` |
