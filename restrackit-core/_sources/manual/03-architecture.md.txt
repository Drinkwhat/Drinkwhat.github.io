# Architecture Overview

## System Design

Restrackit is a FastAPI-based REST API for restaurant inventory management with AI-powered image analysis, designed using a **Modular Monolith** architecture.

```text
┌─────────────────────────────────────────────────────────────┐
│                      Client (App/Web)                       │
└────────────────────────┬────────────────────────────────────┘
                         │ HTTP/REST (JSON)
                         ▼
        ┌────────────────────────────────────┐
        │      FastAPI Application           │      ┌──────────────┐
        │  (app/main.py)                     │◄────►│    Redis     │
        └────────────┬───────────┬───────────┘      │(Cache/Queue) │
                     │           │                  └──────────────┘
    ┌────────────────┼───────────┼────────────────────────┐
    │                │           │                        │
    ▼                ▼           ▼                        ▼
┌──────────┐   ┌──────────┐ ┌─────────────┐        ┌─────────────┐
│ Mobile   │   │ Gemini   │ │ PostgreSQL  │        │ arq Worker  │
│ on-device│   │ Agent    │ │ Database    │        │ (Cron jobs) │
│ OCR      │   │ (AI)     │ │ (Data)      │        │             │
└──────────┘   └──────────┘ └─────────────┘        └─────────────┘
```

## Technology Stack

### Backend

- **Framework**: FastAPI (Python >= 3.14)
- **ORM**: SQLAlchemy 2.0 (Sync/Async ready)
- **Migrations**: Alembic
- **Linter**: Ruff (replaces Flake8/Black/Isort)

### AI & Data

- **OCR**: on-device on the mobile app (ML Kit); the backend receives only text
- **LLM**: Google Gemini 2.0 Flash (via `google-genai` SDK)
- **Database**: PostgreSQL 18 (Alpine)
- **Cache & Queue**: Redis 7.2 (with msgpack serialization)
- **Task Queue**: arq (Async Redis Queue)

### DevOps

- **Container**: Docker (Multi-stage: Builder -> Runtime)
- **CI/CD**: GitHub Actions (Lint, Test, Build, Docs)
- **Testing**: Pytest + Coverage (100% target)
- **Monitoring**: Sentry (Error Tracking) + Apitally (API Analytics)

## Key Components

### 1. Modular Architecture (`app/modules/`)

Each module (`inventory`, `products`) is self-contained with its own:

- **Router**: Defines API endpoints
- **Service**: Implements business logic
- **Models**: Defines DB tables
- **Schemas**: Defines DTOs (Data Transfer Objects)

### 2. Error Handling (`app/core/errors.py`)

Standardized error handling using `AppError` and specific codes (`ERR_...`):

- All errors return a uniform JSON structure.
- Unhandled exceptions are caught by global middleware and returned as 500 System Errors.

### 3. AI Agent (`app/services/ai_agent.py`)

A specialized service that:

1. Receives raw OCR text.
2. Reconciles the extracted product name with the store catalog (exact match, then substring match).
3. Returns structured data (Product, Lot, Expiry, Confidence).

### 4. Caching System (`app/shared/cache.py`)

Implementation of an asynchronous caching layer:
- **Decorator `@cached`**: Applied to service methods (including `products` and `kitchen`) to cache results in Redis.
- **Serialization**: Efficient binary serialization using `msgpack` with custom encoders for `date`/`datetime`.
- **Model Hydration**: Automatically reconstructs Pydantic models from cache hits.
- **Fail-Open**: If Redis is unavailable, the system transparently falls back to database queries, ensuring high availability. A `WARNING` log is emitted for every bypass to make cache degradation visible in observability tooling.
- **Selective Invalidation**: Cache entries are automatically invalidated on resource updates or deletions using key pattern matching.

### 8. ORM Loading Strategy (`app/modules/*/models.py`)

All SQLAlchemy relationships use `lazy="raise"` instead of `lazy="selectin"`:

- **No implicit loads**: accessing a relationship without an explicit `.options()` call raises `InvalidRequestError` immediately, preventing accidental N+1 queries in production.
- **Explicit eager loading**: every service method that returns a response shape requiring related data declares the required `selectinload()` chains in the query's `.options()`. This makes the access pattern visible and reviewable in the service layer.
- **Test suite as guardian**: `lazy="raise"` turns the test suite into an automatic detector for missing eager loads — any unloaded relationship surfaces as a hard error during testing, not as a silent extra query in production.
- **Cascade safety**: `cascade="all, delete-orphan"` collections (`Recipe.ingredients`, `Preparation.items`, `ProductMaster.batches`) retain `lazy="raise"`; SQLAlchemy handles the cascade load implicitly during delete, which is tested and confirmed safe.

### 5. Background Tasks (`app/worker.py`)

Asynchronous task processing using `arq`:
- **Singleton Pool**: Uses a persistent Redis connection pool to minimize overhead.
- **Msgpack Serialization**: Custom serializers for `arq` that handle `date`/`datetime` objects via ISO conversion.
- **Cron jobs**: Daily expiry check (`check_expired_batches_task`) that creates DB notifications per store.
- **Cron jobs**: Daily purge (`purge_ocr_analyses_task`) of OCR analyses older than 90 days.

### 6. Allergen Management (`app/shared/allergens.py`)

A specialized bitmask-based system for EU-compliant allergen tracking:
- **Bitmask Storage**: Allergens are stored as a single integer (bitmask) in the `ProductMaster.allergen_mask` column, ensuring extreme performance for filtering.
- **I18n Support**: Dedicated mapping endpoints (`/products/allergens`) provide localized labels (IT/EN) for frontend display.
- **Strict Typing**: Uses `AppAllergen` Enum to prevent invalid data entry and ensure consistency across the API.
- **Filtering**: Efficiently supports queries like "gluten-free" or "free from X, Y, Z" using bitwise operators in the database.
### 7. OCR Post-Processing (`app/services/ocr_post_processing.py`)

A specialized engine for intelligent lot code correction:
- **Structural Matching**: Uses "structural signatures" (mapping characters to categories like `A`, `N`, or `X` for ambiguous characters) to compare new lots with historical data.
- **Ambiguity Resolution**: Handles common OCR errors (e.g., swapping `0`/`O`, `1`/`I`, `5`/`S`) by validating differences against a known ambiguity map.
- **Context-Aware Boost**: Increases AI confidence score when a lot code matches a known pattern from the product's history, reducing manual revisions.
- **DRY Architecture**: Uses a unified source of truth for ambiguous character pairs, automatically shared between structural matching and positional validation logic.

## Data Flow: Label Text Analysis

1. **OCR on-device**: The mobile app extracts the label text locally (ML Kit).
2. **Upload text**: Client sends the raw text to `POST /inventory/parse-text`.
3. **Agent**: `InventoryAgentService` sends text + store context to Gemini.
4. **Prompt Injection Protection**: Untrusted OCR text is wrapped in delimiters (`[START_OCR]...[END_OCR]`) and isolated using **System Instructions**.
5. **Structured Output**: Enforces valid JSON results via **JSON Schema Mode** and Pydantic models.
6. **Catalog reconciliation**: the extracted product name is matched against `products_master` (exact, then substring); names with no match become `NON_IDENTIFICATO`.
7. **Post-Processing**: `LotCodePostProcessor` compares the extracted lot with historical lots for the same product to correct common OCR ambiguities.
8. **Analysis log**: text, AI proposal (before post-processing) and model are saved in `ocr_analyses` and an `analysis_id` is returned; the client sends it back to `POST /inventory/confirm` (optional), which stores the confirmed values next to the proposal to measure parsing accuracy. Rows older than 90 days are deleted by the daily `purge_ocr_analyses_task` (03:30).
9. **Response**: Structured JSON is returned to the client (including a `warning` if the product wasn't identified).
10. **Confirm**: Client sends validated data to `POST /inventory/confirm` to save in `batches` table. Note: the deprecated `lot_code_ai` field has been removed to simplify the schema.

## Multi-Tenancy & Security

### 1. Row Level Security (RLS)
The system implements a dual-layer isolation strategy:
- **Application Layer**: All service queries are scoped by `store_id` (e.g., `filter(ProductMaster.store_id == store_id)`).
- **Database Layer**: PostgreSQL Row Level Security is enabled on core tables. The application uses a `SET LOCAL app.current_store_id` command within every transaction to enforce isolation at the database level, preventing data leaks even in case of application bugs.

### 2. Authentication (Keycloak OIDC)
- **JWT Validation**: Real-time token validation against Keycloak JWKS with localized caching in Redis for performance.
- **Granular Permissions**: A custom `RequirePermission` dependency maps Keycloak roles to fine-grained action permissions (e.g., `INVENTORY_WRITE`).

### 3. Opaque UUID API IDs

All API path parameters use `public_id` (UUID v4) instead of sequential integer PKs:

- **IDOR prevention**: sequential integers allow enumeration of all resources across stores. UUIDs make enumeration infeasible.
- **Implementation**: `PublicIdMixin` (`app/shared/mixins.py`) adds `public_id UUID UNIQUE NOT NULL` to 9 tables. Routers accept `uuid.UUID` path params; service methods translate to internal integer IDs via a single indexed lookup.
- **Zero FK impact**: internal integer PKs and all FK relationships are unchanged — only the API surface changes.
- **Tables covered**: `products_master`, `categories`, `units_of_measure`, `storage_methods`, `product_storage_rules`, `batches`, `recipes`, `preparations`, `notifications`.

### 4. Monitoring & Observability
- **Request Tracing**: Every request is assigned a unique `X-Request-ID`, propagated through logs, database contexts, and external service calls for end-to-end tracing.
- **Sentry**: Captures unhandled exceptions and performance bottlenecks with release tracking tied to Git commit hashes.
- **Apitally**: Provides real-time insights into API usage, response times, and error rates without impacting performance.
